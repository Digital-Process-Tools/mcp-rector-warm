#216 self-review (oss:auditor pass): `LspServer::codeAction()`'s new #216 recompute-before-edit
guard forces `EditDiagnosticsSource::diagnoseForEdit()`/`diagnoseBufferForEdit()` right before
building a `WorkspaceEdit`, and treats an empty `fixes` result from that fresh call the same as "no
fix here" (`return $this->result($id, [])`). `RectorDiagnosticsSource::interpret()` (unchanged by
#216) returns the identical `['fixes' => [], 'errors' => [...]]` shape both for "nothing to fix" and
for a genuine failure (a SecurityError, an exception, an unparseable report). Before #216, codeAction
never made a second Rector call at all, so this ambiguity could only ever surface through the
earlier, already-published `diagnose()` diagnostic. After #216, the forced-noSession recompute is a
brand-new call on the code-action request path specifically, and if IT fails for a reason the
earlier (possibly session-served) `diagnose()` call did not hit, the editor silently sees "no code
actions" -- indistinguishable from "Rector found nothing here" -- with `$fresh['errors']` dropped on
the floor and only `interpret()`'s own stderr line as a trace, which the editor UI never shows.

Auditor's own assessment: `misreports` (an output-rendering ambiguity, not data loss or a wrong
write), non-blocking. No test exercises `diagnoseForEdit()`/`diagnoseBufferForEdit()` returning a
non-empty `errors` array alongside an empty `fixes` array on the code-action path specifically --
`LspServerTest::testCodeActionRecomputesTheEditWithTheSessionForcedOffWhenTheSourceSupportsIt` and
its buffer-path sibling in `LspServerBufferTest.php` only exercise the success case.

Not decided here: whether this is worth a `window/showMessage` warning on the codeAction response
(fixWorkspace's own `errors` already surface that way for its whole-tree case, see
`LspServer::executeCommand()`'s `describeWorkspaceFixErrors()`), whether codeAction has anywhere to
put such a warning in the LSP codeAction response shape at all, or whether this is simply an
acceptable, pre-existing ambiguity (the SAME ambiguity existed for the original `diagnose()` call,
just not on this specific request path) that is not worth a new mechanism for.
