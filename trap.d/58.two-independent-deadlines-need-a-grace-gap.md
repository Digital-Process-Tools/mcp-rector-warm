What was observed: implementing #58's --call-timeout, I put an identical deadline
(same $callTimeoutSeconds, both computed from hrtime(true) at roughly the same instant) on
two independent loops -- forkAndExecute()'s wait loop inside the worker (waiting on its own
forked grandchild) and runForked()'s read on the persistent worker<->daemon socket. The
intent was "the worker's own deadline fires first and cleans up; the daemon-side one is only
a backstop for a genuinely unresponsive WORKER." With both set to the same value, the new
unit test (a 1s deadline, sleep(30) grandchild) failed on the assertion that the worker
survives a single timed-out call -- the daemon-side deadline fired too, at nearly the same
instant, and killed the worker itself as collateral.

Where: src/RectorRunner.php, forkAndExecute()'s wait loop vs. runForked()'s deadline
(originally both `$this->callDeadlineNs()` with no argument).

What it cost: one red run of
tests/Unit/RectorRunnerTest.php::testWedgedCallIsKilledAtTheDeadlineAndTheWorkerStaysUsable,
plus the time to work out why (SIGKILL + pcntl_waitpid + one writeFrame() back to the daemon
is not free, and none of that overhead happens before the worker's own deadline is already
reached -- so a same-instant daemon-side deadline can trip concurrently with, not only after,
the inner one).

How it was confirmed / fixed: gave the daemon-side (outer) deadline a fixed grace period on
top of the worker-side (inner) one -- callDeadlineNs(int $graceSeconds = 0), called as
callDeadlineNs(self::RUN_FORKED_DEADLINE_GRACE_SECONDS) (5s) in runForked() and
callDeadlineNs() (no grace) in forkAndExecute(). Re-ran the same test: green, worker survives.

Possibly a real rule, possibly too narrow to this one file's shape (two loops racing on the
same clock): whenever two timeout mechanisms are meant to be inner/outer (one a cleanup step,
the other a backstop for when the cleanup step itself doesn't run), they need a strictly
positive grace gap between them, sized to the cleanup step's own worst-case cost -- not
merely "computed from the same deadline value."

Addendum (self-review, Explore pass on the same diff): the 5s I picked is a fixed heuristic,
tuned against exactly one green run of the 1s-deadline unit test above -- not against any
adversarial or loaded scenario. Under the exact conditions that would make a call look
"wedged" in the first place (the host under heavy load, swapping, near OOM), the cleanup
step's own cost (SIGKILL + pcntl_waitpid + one writeFrame()) is more likely to exceed 5s, not
less -- which is precisely the case this grace period exists to rule out. Nothing here
measures that cost under load; the 5s is a reasonable engineering default, not a derived
bound, and no test exercises the boundary itself (only the happy path where 5s is obviously
enough). If this ever becomes a real rule, whatever promotes it should also ask whether a
FIXED grace period is right at all, or whether it should scale with the deadline it is
guarding (a 600s default call-timeout and a 1s test deadline are very different regimes for
the same "5s ought to be enough" assumption).
