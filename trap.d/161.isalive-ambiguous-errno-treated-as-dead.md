While fixing #161/#162 and self-reviewing the fail-direction fix for
`TempCopySweeper::isReparsePoint()` (commit 6921a41), a second-pass review spawn found an
unaddressed instance of the same "cannot actually tell, so treat it as safe to proceed" shape,
in the same file, feeding the same `removeIfStale()` gate -- but pre-existing (introduced in
b133eb4, not touched by this lane's own diff), so out of scope to fix here.

`TempCopySweeper::isAlive()` (src/Lsp/TempCopySweeper.php) documents a three-way contract in its
own docblock: "true = alive, false = known dead, null = cannot tell (kept)". `removeIfStale()`
only proceeds to `unlink()`/`rmdir()` when `isAlive($pid) === false` (line 104: `... ||
self::isAlive($pid) !== false`).

The POSIX branch never actually returns `null`:

```php
if (function_exists('posix_kill')) {
    if (posix_kill($pid, 0)) {
        return true;
    }
    // EPERM: the process exists but belongs to someone else.
    return function_exists('posix_get_last_error') && posix_get_last_error() === 1 ? true : false;
}
```

If `posix_kill()` fails for any errno other than EPERM (1) -- not ESRCH (3, genuinely dead), some
other errno, or `posix_get_last_error()` itself unavailable -- this collapses straight to `false`
("known dead"), which is exactly the ambiguous "cannot tell" case the docblock's own contract
says should be `null` ("kept", i.e. not deleted). `removeIfStale()` reads that `false` as
permission to `unlink()`/`rmdir()`.

Not fixed here: the honest fix is straightforward (check `posix_get_last_error()` against ESRCH
explicitly for `false`, EPERM explicitly for `true`, anything else -- including the function being
unavailable -- for `null`), but a red-first test needs `posix_kill()` to fail with a **specific
third errno**, and there is no portable, deterministic way to force that from a PHPUnit test
(unlike EPERM, which a real permission-denied pid can produce, or ESRCH, which a genuinely dead
pid produces naturally via the existing `deadPid()` helper). Shipping the fix without a red test
that actually exercises the branch felt worse than leaving it named here for `/oss:curate` (or a
future lane with more room) to decide whether it is worth a mocked/reflection-based test or a
narrower argument that the risk is acceptable as-is.

Ranked against the findings table: `fails-to-preserve` -- a safety property (never delete a pid's
temp directory while genuinely unable to confirm it is dead) silently stops holding on one
specific, narrow-trigger branch. Non-blocking per that row.
