While building #218 (coverage collection for pcntl_fork children / proc_open
subprocesses), debugging ad-hoc PHP snippets that inspected
`CodeCoverage::getData()->lineCoverage()` directly produced false-positive "hit" counts.

Observed: `lineCoverage()` returns, per file, an array keyed by line number, where each
value is an ARRAY of test/process-id strings that executed that line -- not an integer
count. An unexecuted-but-coverable line has value `array(0) {}` (empty array), not `0`
and not `null`.

A naive check like `$v > 0` to mean "was this line hit" is wrong and, worse, silently
wrong in the dangerous direction: in PHP, comparing an array to a non-array int always
evaluates the array as greater (`[] > 0` is `true`). So `array_filter($lines, fn($v) =>
$v !== null && $v > 0)` counts EVERY coverable line as "hit", including ones that never
ran.

This cost roughly 40 minutes chasing a phantom "phpcov merge silently drops coverage for
this file" bug: individual raw `.cov` files all appeared to show full coverage (because
of the `$v > 0` bug), while the final merged Clover XML correctly showed 0% (Clover reads
the real `count=` attribute, an actual integer, so it was never wrong) -- the two were
compared and taken as contradictory evidence of a merge-pipeline defect, when in fact the
Clover number was right all along and the "raw" number was a debugging-script artifact.

Correct check: `$v !== null && count($v) > 0`.

Not sure whether this is specific to `fromXdebugWithoutPathCoverage()`'s representation or
a general property of `RawCodeCoverageData`/`ProcessedCodeCoverageData` in
phpunit/php-code-coverage 10.1.x -- worth confirming before generalising into a rule.
