RectorRunner::collectIniOverrideArgs() (#125) splices `-d name=value` pairs into the
no-pcntl standby worker's proc_open() command array. On Windows, proc_open()'s array-form
command still gets flattened into a single command-line string internally (CreateProcess has
no native argv, unlike POSIX execve), applying PHP's own quoting rules to each element.

Flagged by the oss:auditor self-review spawn on this diff (ranked `splices`, non-blocking per
skills/manager/phases/findings.md's ranking table -- the value originates from the maintainer's
own machine/php.ini, not forge text, so it does not rank as `forges`). The auditor confirmed
this repo's own daemon entrypoints (bin/mcp-rector-warm, bin/rector-warm-lsp) only ever
ini_set() space/quote-free values (display_errors=stderr, memory_limit=-1), so the
windows-latest CI leg does exercise collectIniOverrideArgs() producing a real non-empty -d list
through a real Windows proc_open() call -- but never with a value containing a space or a
quote, which is exactly the shape a user's own -d flag would take on Windows (e.g.
`-d error_log="C:\Program Files\...\log.txt"`), the case #125 exists to forward correctly.

Not verified: run the daemon on a real windows-latest box with a -d flag whose value contains
a space or a quote and confirm the standby worker's own resolved ini setting matches. No CI leg
and no test added by this lane exercises that specific shape.

Update (same lane, later commit): a second independent E2E review found the forwarded values
were not being quoted for PHP's OWN ini-value parser at all -- an unquoted value ending in a
reserved character (space, `(`, `;`) truncates silently. Fixed by wrapping every forwarded value
in double quotes (RectorRunner::quoteIniValue()), with backslash/quote escaping, verified
end-to-end on this lane's own platform (macOS) via a real php subprocess. This makes the
Windows-specific risk this fragment names MORE pointed, not resolved: every forwarded value now
deliberately contains literal `"` characters, which is exactly the shape proc_open()'s Windows
CreateProcess-level command-line flattening is most likely to mishandle (it must re-escape an
already-quoted argv element into its own single command-line string). Still not verified on a
real windows-latest box.
