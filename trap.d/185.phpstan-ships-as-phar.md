#185 (session-child dependency tracking): the design this issue proposes -- and
the external prototype it references -- hooks `PHPStan\Parser\CachedParser` and
`PHPStan\BetterReflection\SourceLocator\Located\LocatedSource` by `require`-ing a
same-FQCN shadow file before the real class is ever autoloaded (PHP skips the
autoloader once a class name is already declared). That trick assumes the real
class exists as a plain, on-disk `.php` file somewhere under `vendor/`.

In this repo's actual dependency tree (`rector/rector: ^2.4`, resolved to 2.6.7,
pulling `phpstan/phpstan: ^2.2.14`, resolved to 2.2.16) it does not: `grep -rl
"class CachedParser" vendor/` and the equivalent for `LocatedSource` both return
zero matches anywhere under `vendor/`, including inside `vendor/rector/rector`'s
own bundled/scoped copy. `composer show phpstan/phpstan` confirms the package
IS installed, but `du -sh vendor/phpstan/phpstan` is 48 MB and `find
vendor/phpstan/phpstan -maxdepth 2` shows why: the package ships almost nothing
but `phpstan.phar` (plus a thin `bootstrap.php`). PHPStan's own source -- and
the `ondrejmirtes/better-reflection` fork it bundles -- lives INSIDE that phar,
reachable only via the `phar://` stream wrapper:

    php -r '$p = new Phar("vendor/phpstan/phpstan/phpstan.phar");
    foreach (new RecursiveIteratorIterator($p) as $f) { echo $f->getPathname()."\n"; }'
    # -> phar://.../phpstan.phar/src/Parser/CachedParser.php
    # -> phar://.../phpstan.phar/vendor/ondrejmirtes/better-reflection/src/SourceLocator/Located/LocatedSource.php

The `require`-before-autoload shadow trick still works against a phar-hosted
class (the class name is what PHP checks, not where the defining file lives),
but this repo has no cheap way to notice a PHPStan/Rector version bump changed
either class's shape: the shadow file would need extracting from the CURRENT
phar and diffing on every dependency update, not just read once. On the version
resolved during this investigation (rector/rector 2.6.7 -> phpstan/phpstan
2.2.16), both classes were confirmed byte-for-byte identical to the external
prototype's own frozen copies except for the prototype's own instrumentation
lines (verified with `diff` against files extracted straight out of the phar
into /tmp) -- so the trick is sound TODAY, but nothing in this repo enforces
that it stays sound after the next `composer update`. Whoever wires the actual
session-child mechanism needs a runtime guard (e.g. hash the extracted phar
source against a known-good value at session-boot time, falling back to the
existing safe fork-per-call path on any mismatch) rather than trusting a
one-time diff done by hand during a single investigation.
