#127's self-review (oss:auditor) found: `boot()` captures `$daemonPid = \getmypid();` before
forking and passes `$daemonPid !== false ? $daemonPid : null` into `serveWorker()` ->
`forkAndExecute()`. If `getmypid()` ever genuinely returns `false` (the PHP manual leaves this
theoretically possible, and the code already guards for it defensively), the worker is started
with `$daemonPid = null`, which inside `forkAndExecute()`'s wait loop takes the exact same
"skip the whole orphan check" branch the pre-#127 code always took -- silently, with no log line
and no distinguishing exit code.

The result: an operator watching this worker cannot tell "the daemon is fine, nothing to report"
apart from "I could not learn my own pid, so the #127 kill-detection this very fix shipped is
simply off for this one call." Both render identically: the worker just keeps running.

Ranked non-blocking (`misreports` in findings.md's table) -- the fix (if one is ever wanted) is
almost certainly "log a line when daemonPid is null before entering the wait loop", not a
structural change, and `getmypid()` returning `false` is a documented-but-essentially-never-seen
edge case in real PHP builds -- not something to spend a design decision on inside issue #127's
own diff. Logged here rather than fixed in place or filed, per the finding's own ranking.

Confirmed by reading `src/RectorRunner.php`'s `boot()` (the getmypid() capture) and
`forkAndExecute()`'s wait loop (the `$daemonPid !== null` gate before the orphan check runs) --
no reproduction attempted (forcing `getmypid()` to return `false` is not practically achievable
from a test).
