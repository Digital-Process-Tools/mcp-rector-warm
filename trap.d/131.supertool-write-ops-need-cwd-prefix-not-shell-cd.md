supertool's own writes (`edit:@-`, `paste:@-`) do NOT follow a preceding `cd DIR &&` in the
same call the way one might expect: the harness resets cwd between separate Bash tool calls
(per the environment note), so a bare `supertool 'edit:@-' <<'TOML' ... TOML` call with no `cd`
prefix in THAT SAME call resolves against the harness's default cwd -- in this session, the
primary clone (`<host-home>/mcp-rector-warm`), not whichever worktree an
earlier call had `cd`'d into.

What it cost: two write ops (`edit:@-` on `src/Lsp/LspServer.php`, `edit:@-` on
`tests/Unit/Lsp/LspServerBufferTest.php`) landed silently in the main clone instead of the
lane's own worktree (`<host-home>/mcp-rector-warm-wt/131`). Both edits
applied cleanly and reported success -- the only tell was the trailing `[branch: main]` line
in the edit receipt, easy to skim past, versus the expected `[branch: fix/131]`. Discovered
only when a later `git stash`/read cycle (correctly run inside the worktree via a fresh `cd
... && ...` call) showed the file unexpectedly clean -- the edits were never there to begin
with, because they had gone somewhere else. Fixed by `git checkout -- <files>` in the main
clone (reverting only those two paths, leaving the clone's other pre-existing dirty files
untouched) and redoing both edits with an explicit `cwd:ABSOLUTE_PATH` op prefixed as its own
argument -- `supertool 'cwd:/abs/path/to/worktree' 'edit:@-' <<'TOML' ...` -- which the
`edit:@-` receipt then confirmed via the matching `[branch: fix/131]` line.

Two failed attempts before that: `cwd:.:edit:@-` (colon-chained) fails with `cwd: not a
directory: ...` -- `cwd:PATH` must be its own separate quoted argument, not colon-joined to
the next op, per `supertool 'help:cwd'`. And passing an absolute path directly to `path =` in
the payload without `cwd:` refuses with `path escapes cwd` when the process's actual cwd is
the main clone and the absolute path points into a different worktree.

How to spot it happening again: read the receipt's trailing `[branch: ...]` line on every
write op and confirm it names the lane's own branch, not the repo's default branch or
whatever branch the primary clone happens to be on.
