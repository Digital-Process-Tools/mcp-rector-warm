In PHPUnit 10+, `AssertionFailedError` extends `\RuntimeException`. The four
process-kill deadline tests (`RectorRunnerProcessTreeKillTest::testColdCallKilledAtItsDeadlineLeavesNoProcessBehind`
and siblings, `RectorRunnerTest::testColdCallIsKilledAtItsDeadlineWithoutPcntl`)
wrap their assertion in `catch (\RuntimeException $e)`, around a code path that
also calls `self::fail('expected ... to be killed ...')` on the non-killed
branch. `self::fail()` throws `AssertionFailedError`, which that same `catch`
then re-catches as if it were the expected "process was killed" runtime
exception -- so the test's own negative assertion (`assertStringContainsString`
against the caught exception's message) was checking `self::fail()`'s own
message text, not the thing it meant to assert.

Where: the four tests above, discovered while diagnosing #230's coverage-leg
CI regression (PR #243). The real regression (a Rector worker subprocess
racing its own prefixed react/promise autoload against this project's real
one under the coverage job's auto_prepend_file) made `run()` return normally
with `exit_code: 1` well before any real deadline -- the self-catch masked
that the tests were passing for the wrong reason (a string-match against
`self::fail()`'s own text) rather than ever observing a real kill.

What it cost: the first fix attempt (04bcd51, pcov.exclude for vendor/) was
plausible, shipped, and did not fix anything -- the true cause took a second,
deeper investigation (direct reproduction bypassing phpunit/CI) to find,
because the test's own failure message read like a genuine "kill message not
found" rather than "self::fail() caught itself."

How it was confirmed: fixed in 68d890c by making the worker invocation path
a no-op for `tests/coverage/prepend.php`, verified with 10/10 reproduced wedge
failures before the fix and 0/8 after (pcov on), 10/10 still failing with only
04bcd51's vendor pcov.exclude applied (proving that fix never addressed the
trigger).

Not fixed here: the four tests' own `catch (\RuntimeException $e)` is still
broad enough to swallow their own `self::fail()`. Should assert the caught
exception is not an `AssertionFailedError`, or restructure so `self::fail()`
cannot be self-caught -- a "must fire" positive-control case (CLAUDE.md's own
"pair every must-not-fire with a must-fire") would also have caught this
earlier. Non-blocking (`misreports` class per findings.md: a test-harness
false-report, not the production write path) -- a later `rector process`
code path is not affected, only the trustworthiness of this one failure
message.
