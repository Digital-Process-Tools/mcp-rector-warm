Gate-3 release audit finding (v0.7.2..HEAD, round 1) on #189's session spawn
path (src/RectorRunner.php:1245-1253, spawnSession's handshake read):

The session child runs all of its startup -- SessionHooks setup, the
staticInputFiles() walk that sha1_file()s every scanned file, and the watch
paths -- before the handshake, under the call's own --call-timeout deadline.
If that deadline elapses during startup, spawnSession() throws "rector call
exceeded ...; the analysis was killed". It does not call forkAndExecute() and
it does not call disableSession() -- so the fallback #189 documents for every
other declined/lost-session route does not run on this one.

What it costs (reasoned, not observed): the error blames "the analysis",
which never started, and misleads whoever reads it. Because nothing disables
the session, the next call spawns again and can fail identically -- a call
that could have succeeded via the plain fork fallback times out instead.

Ranked non-blocking (misreports): narrow in practice (needs a --call-timeout
smaller than session-startup time, which matters mainly on a very large
project with many autoload paths), and the fix -- either extending the
startup/handshake window's own timeout budget, or treating a startup timeout
as "declined, fall back to forkAndExecute()" -- is a session-lifecycle
decision better made once real timing data exists.

How it would be confirmed: MCP_RECTOR_WARM_SESSION_LOG=1's spawn-timing line
on a large project with many autoload paths, measured against the smallest
--call-timeout anyone configures; or a test with an artificially tiny timeout
and a large watch directory.
