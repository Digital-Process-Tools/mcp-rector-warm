What was observed (self-review, oss:auditor pass on the #48-verification commit,
4a5e494): two non-blocking notes on the new tests/E2E/mcp_harness.py process-tree check
(daemon_pid()/process_descendants()/assert_no_zombie_descendants()).

1. `ps -eo pid,ppid,stat` is a GNU/procps-ng column spec. This repo's CI runs the E2E
   suite on ubuntu-latest only (.github/workflows/tests.yml has no macOS/BSD/Windows
   leg for any of its three jobs), so this is genuinely never exercised anywhere except
   procps-ng. The function's own docstring already discloses this ("not verified against
   a BSD/macOS `ps` column layout... since CI never runs this on anything but
   ubuntu-latest"), so this is an honest gap, not a silent one. If a maintainer ever runs
   this suite locally on macOS, `process_descendants()` would likely raise loudly (via
   the returncode check added in the same self-review round) rather than misbehave
   quietly, since BSD `ps` either rejects this exact flag combination or produces a
   different column layout `parts[2]` would mis-parse -- not confirmed, reasoned only.
   Where: tests/E2E/mcp_harness.py, process_descendants().

2. Only the forkAndExecute()-path wedge (a wedged CALL, exercised by
   wedged-call-over-call-timeout.yaml's Wedged.php step) gets the real `ps`-based
   zombie check. The boot()-path wedge (a hanging rector.php/bootstrap file, added in
   the same commit) is only covered by tests/Unit/RectorRunnerTest.php's
   testWedgedBootIsKilledAtTheDeadline, which asserts the exception message/elapsed
   time/isWarm() state but never snapshots the daemon's real process tree via `ps` --
   there is no E2E scenario driving a wedged BOOT (as opposed to a wedged call) through
   the harness's new process-tree check. The boot-path SIGKILL+reap code is structurally
   identical to the already-covered call-path code (same killAndReap() helper after this
   same self-review round), so this is a coverage gap rather than a known-different
   behaviour, and adding it would need a new scenario whose FIRST call step wedges
   during boot (before the harness has a live worker to talk to at all) -- a real
   E2E scenario could be built following the same shape as wedged-call-over-call-timeout.yaml,
   just with the sleep() moved into the config's own top level instead of inside a
   rule's refactor().

What it would cost to fix: item 1 is not really fixable without a second `ps` codepath
per platform, and CI never exercises the platform it would matter on, so it may not be
worth a fix at all (the auditor's own words: "arguably not even worth a trap.d fragment
given the honest docstring disclosure already in place" -- logging it anyway per this
directory's own "hesitating is the failure this removes" instruction). Item 2 is a real,
buildable E2E scenario that was not added in this round for time/scope reasons (the
maintainer's ruling was answered by the unit test + the existing E2E zombie check on the
call path; a boot-path E2E zombie check was not explicitly asked for).
