Finding from self-review (oss:auditor, Class A) on the #33 fix (bootstrap-file
change detection, commit 3006ebb, src/RectorRunner.php): resolveBootstrapFileHashes()
catches \Throwable around the call to \Rector\Configuration\Parameter\SimpleParameterProvider
::provideArrayParameter('bootstrap_files') and returns [] on any failure. That [] then
flows unchanged into configFileChanged()'s new comparison loop and into the worker's
boot handshake ('bootstrap_files' key). The caller cannot tell "this rector.php
genuinely registered no bootstrap files" from "bootstrap-file resolution silently
failed" -- both render as the identical empty map, with no log line or response field
distinguishing them. If SimpleParameterProvider (or Option::BOOTSTRAP_FILES's string
value) ever moves upstream, #33's whole fix goes silently inert: no error, no reboot
on a bootstrap-file edit, just a quiet return to the pre-fix behaviour.

Ranked fails-to-preserve (non-blocking) by the auditor -- the fix is "log/report when
the try fails", not "change what happens on success". This mirrors an EXISTING,
apparently deliberate pattern a few lines below in the same file (execute()'s
ConfigInitializer::areSomeRectorsLoaded() check also fails open on \Throwable), so it
may be an accepted house style for "defensive against an upstream rename" rather than
an oversight specific to this diff -- worth a maintainer's one-line confirmation of
which it is, and whether the house style should include a stderr line (this class
already writes to stderr via display_errors=stderr, so a `fwrite(STDERR, ...)` on the
catch branch would be one line and would preserve the fail-open behaviour while
making the silent case visible in server logs).

Observed: read only, not reproduced by forcibly breaking SimpleParameterProvider's
resolution (would require patching vendor/rector/rector, out of scope for a fragment).
