Raising PHPStan to level 7 (#211) forced several `|false`-returning stdlib calls
(`getmypid()`, `sha1_file()`, `getcwd()`, `stream_socket_pair()`, and an
`array_filter(..., is_string(...))` narrowing of a JSON-decoded `argv`/`call_argv`
array) into a real type by adding a runtime check at each site.

Two of those checks (found by the oss:auditor review spawn on this PR, not by the
lane itself) resolve the `false` branch by silently producing a SMALLER/EMPTY
result rather than failing loudly, in a diff whose OWN established pattern
elsewhere is to fail loudly (`ruleSkippedFor()` now throws `RuntimeException`
rather than degrade; `$this->procWorker` gets `\assert($this->procWorker !== null)`):

1. `bin/rector-cold-call.php` and 4 sites in `src/RectorRunner.php` --
   `array_values(array_filter($request['argv'], is_string(...)))` silently drops
   any non-string element from argv rather than asserting the array was already
   all-strings. The commit's own justification ("already impossible in practice,
   since the daemon always builds this array as list<string> before encoding it")
   is probably correct, but nothing enforces the premise -- if it is ever wrong,
   warm's write path silently gets a shorter argv than cold would, which is
   exactly the class of defect CLAUDE.md's "writes equal cold" rule cares most
   about catching, and CI's `--dry-run` cannot catch an extra/different change.

2. `bin/rector-warm-orphan-watchdog.php:120-121` --
   `$selfPid = \getmypid(); ProcessTree::killTree($workerPid, $selfPid !== false ? [$selfPid] : []);`.
   If `getmypid()` ever returns `false` here, the exclude-list degrades to `[]`,
   which is the one case `ProcessTree::killTree()`'s own docblock says causes a
   watchdog self-deadlock (SIGSTOP mid-kill, reproduced empirically per #245's own
   trap.d fragment). Checked by hand: this is NOT a new regression -- the OLD
   code (`[\getmypid()]`) passed `[false]` in this same case, and `array_diff()`
   string-casts its operands, so `(string) false === ''` never matched a real
   pid's digits either. Old and new code are behaviourally identical on this
   branch; #211 only made the `|false` union visible to PHPStan, it did not
   create or worsen the gap. Argued down as a fix *for #211 specifically* on
   that basis, but the underlying dormant self-deadlock risk (what happens on
   the actual, if rare, `getmypid() === false` case) was never fixed by anyone
   and is worth a dedicated look.

Neither is ranked as blocking #211 itself (per findings.md's table: non-blocking,
`trap.d/`-eligible). Left here rather than fixed in #211 to keep that PR's blast
radius to "raise the level, fix every real error" -- a loud
`\assert()`/exception at each of these 5 sites would be a reasonable follow-up,
matching the pattern #211 already uses twice.
