Round-4 release-delta audit finding while fixing #165, in `TempCopySweeper::isReparsePoint()`
(src/Lsp/TempCopySweeper.php, lines 156-183).

The #165 brief's framing of this finding (copied verbatim from the round-4 audit) was: "#162 made
proc_open spawn failure fail closed (correct for safety), but now ANY reason fsutil can't answer
(access denied, proc_open globally unavailable, etc.) renders as 'is a junction' -- diagnoseBuffer()
then always refuses, and sweepTree() silently skips every directory."

Reading the actual code, this framing does not hold as stated. Only ONE condition returns `true`
("is a junction", fail-closed): `!is_resource($process)`, i.e. `proc_open()` itself failing to spawn
the child at all (line 171-173) -- and the method's own self-review comment right above it (lines
161-170) explicitly documents this as the intended fail-closed direction, matching #162's own fix.
Every OTHER way the query can fail to give a clean answer -- `fsutil` running but exiting non-zero
(access denied, the path not existing, an unrecognised `fsutil` error) -- falls through to
`proc_close($process) === 0` (line 182), which is `false` ("not a junction") for any non-zero exit
code. That is the OPPOSITE of "fail closed": a query that ran but could not confirm cleanly is read
as "definitely not a junction", the same silent-fail-open shape #142/#144/#161/#162 were all written
to close.

So there may be a real, narrower defect here -- just not the one as described. If `fsutil` can exit
non-zero for a reason OTHER than "genuinely not a junction" (e.g. permission denied on the path, a
transient I/O error), `isReparsePoint()` currently reports `false` for that case too, which is a
fail-OPEN gap parallel to (but distinct from) the one #162 already closed for the spawn-failure case.
Whether `fsutil reparsepoint query` on a real Windows host ever exits non-zero for a reason that is
not "not a reparse point" was not established here (no Windows host available; reasoned, not
observed) -- worth an experienced Windows engineer or a real Windows CI leg confirming actual `fsutil`
exit-code semantics before this is designed into a fix, since a wrong assumption in either direction
(treating "genuinely not a junction" as fail-closed would break normal sweeping; treating "could not
tell" as fail-open reopens #142/#144's class) is not itself testable from this scratchpad.

Not fixed here: out of scope for #165 (different file, needs the above uncertainty resolved first).
Reasoned, not observed -- no Windows host available in this environment, and no CI leg here disables
proc_open to exercise even the confirmed spawn-failure branch.

Ranked against the findings table: if the reasoning above holds, `misreports`/`overexposes` --
`proc_close() !== 0` collapsing to "not a junction" understates what the check actually confirmed.
Non-blocking: needs a real Windows fsutil exit-code investigation before it is even a confirmed
defect, let alone before a fix is designed.
