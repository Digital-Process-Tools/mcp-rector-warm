While self-reviewing #100's fix (`RectorDiffParser::buildFixes()` attributing a single
leftover applied rule to a single unattributed hunk), an independent `Explore` review pass
found a real residual ambiguity the "exactly one hunk unattributed + exactly one rule
unaccounted for" gate does not actually rule out.

Scenario: a rule fires on TWO separate hunks in the same file, but `changes[]` (Rector's
own per-change attribution) only reports a line for ONE of them -- the second hunk is then
genuinely unattributed by closest-hunk matching, same as the case the #100 fix is meant to
resolve. If a second, unrelated rule was also applied to the file but never produced a hunk
of its own (fully absorbed into another hunk's diff, or not represented as its own hunk at
all), the leftover-rule set has exactly one entry and the unattributed-hunk count is exactly
one -- the gate fires and attributes the SECOND rule's name to a hunk the FIRST rule actually
produced. `buildFixes()`'s own inputs (a diff string, `appliedRectors`, `changes[]`) carry no
way to distinguish this from the genuinely-unambiguous case, because Rector's
`--output-format=json` report does not expose a per-rule hunk count anywhere the parser can
see.

How it was confirmed: constructed a two-hunk diff with `appliedRectors=['RectorA','RectorB']`,
`changes=[['rector'=>'RectorA','line'=>75]]` (RectorA attributed to hunk0 via closest-hunk
matching, hunk1 left unattributed) and ran `RectorDiffParser::buildFixes()` directly via
`php -r` against the real source -- hunk1 came back attributed to `RectorB`, which in this
constructed scenario is wrong (RectorA is the true cause; RectorB never touched the file's
hunks at all). No test in the current diff exercises this specific shape (one rule spanning
two hunks with only one reported by `changes[]`, combined with a second rule producing zero
hunks) -- it is a narrower case than the diff's own "two unattributed hunks, one leftover
rule stays generic" negative control covers, because here the count-based gate still reads
as "exactly one and exactly one" and fires.

A narrower guard than the count comparison currently used -- e.g. cross-checking against how
many separate line ranges a rule's own `changes[]` entries span within the diff, if Rector's
report is ever extended to carry that -- would close this, but is out of scope for #100's
existing heuristic and was not attempted here; presentation-layer severity (a diagnostic
label), not correctness/security, and the maintainer may reasonably decide the residual
false-positive rate is acceptable versus the previous always-generic fallback.
