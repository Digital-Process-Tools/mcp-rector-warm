Gate-3 release audit finding (v0.7.2..HEAD, round 2) on #189's WarmSession/
DependencyFileTracker wiring (src/Warm/WarmSession.php:104, :159-169; src/Warm/
DependencyFileTracker.php:95-104):

DependencyFileTracker::record() has a TOCTOU guard (a $readSha argument -> a
"pendingStale" path) for a file that changes between when a caller reads it
and when it records that read. The only production caller is
WarmSession::recordRead, and it always passes null (the sole `->record(`
call site in src/). So the guard exists and never runs.

This is harmless for TrackingParser's own paths, which report before the
read. It is not harmless for afterInSessionCall(): it records the analysed
file and every file PHP included during the call AFTER the call returns.
TrackingParser.php:14-17 already names this exact ordering as the one that
"would record the newer bytes and hide the change forever".

What it costs (reasoned, not observed): a file first included during a call
and edited before that call returns is tracked with its post-edit signature.
The session keeps the old in-process definition and never reports itself
stale -- warm != cold with no signal, for the length of one call.

Ranked non-blocking (misreports): the window is narrow (one call's
duration), and the fix is to thread a real pre-call hash through
afterInSessionCall() into record() rather than leaving the guard permanently
dark.

How it would be confirmed: a WarmSessionTest case that edits an included file
between the include and afterInSessionCall(), and asserts staleReason() !==
null afterward. Reasoned to fail today.
