Observed while implementing #72 (never-kill-a-write-call correction): running
the full `tests/Unit/` suite occasionally (roughly 1 in 4-5 runs on this
machine) flips `RectorRunnerTest::testWedgedCallIsKilledAtTheDeadlineAndTheWorkerStaysUsable`
from asserting the grandchild-level timeout message
("rector call exceeded 1s (--call-timeout); the analysis was killed") to the
daemon-side backstop message instead ("rector call exceeded its configured
--call-timeout waiting on the warm worker") -- i.e. `runForked()`'s own
`RUN_FORKED_DEADLINE_GRACE_SECONDS = 5` grace over `forkAndExecute()`'s
identically-timed deadline gets eaten by CPU contention when many `sleep()`-
based wedge tests in this same file run back-to-back (this repo's suite is not
parallelized, so it is genuine machine-load contention, not a race between
tests). Reproduced by running `./vendor/bin/phpunit --no-coverage tests/Unit/`
several times in a row; the SAME test in isolation
(`--filter testWedgedCallIsKilledAtTheDeadlineAndTheWorkerStaysUsable`) passed
every time it was tried alone. Not fixed here: it is not caused by #72's own
change (the assertion pins a pre-existing #58 mechanism, unmodified by this
diff, just reached with an extra `bool $dryRun` in scope that is `true` for
that call). Possibly worth a wider grace period, or asserting on a message
pattern common to both kill sites, but that decision needs the tests/Unit/
file held at once, which is not where a single-issue lane is positioned.
