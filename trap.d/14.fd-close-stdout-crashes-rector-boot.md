Tried, for #14/#15: closing the PHP `STDOUT` resource in `bin/mcp-rector-warm` (via
`fclose(STDOUT)`) and reopening the freed fd 1 aliased to stderr's target, keeping the
real MCP pipe alive separately via an earlier `fopen('php://fd/1', 'wb')` dup. The
technique itself works in isolation (verified with a standalone script: `echo` and
`fwrite(STDOUT, ...)` after the close+reopen land on stderr, not the dup'd real pipe).

It breaks something inside a REAL Rector container boot, though: with a genuine
rector.php present and `RectorContainerFactory::createFromBootstrapConfigs()` actually
running, the whole PHP process exits 255 with **zero bytes on stdout or stderr** --
no exception, no fatal-error message, nothing a parent process (or the MCP client
reading it) can see. Confirmed by disabling forking (`canFork() => false`) so the
crash isn't fork-related: same silent 255 either way. Confirmed by reverting only the
`fclose(STDOUT)`+reopen step (leaving the dup'd `$mcpStdout` handle and
`display_errors=stderr` in place): the crash disappears and the call succeeds
normally, just with the pre-existing #15 leak (rector.php's own `echo` reappears on
raw stdout, uncaptured) -- confirming the close+reopen specifically is the trigger,
not the dup, not display_errors, not the container boot itself.

Best guess (not verified further): something inside Rector's Symfony DI container
build (or PHPStan's bootstrap) checks `is_resource(STDOUT)` / calls
`stream_isatty(STDOUT)` or similar during a normal, no-error boot path (not only on
the SymfonyStyle-warning path #14 is about) -- disabling the config-missing check
with `if (false && ...)` and running the same crash repro produced exactly a
`stream_isatty(): supplied resource is not a valid stream resource` PHP warning as
the *visible* symptom in one PHPUnit run once STDOUT was closed, so something in this
dependency chain really does read the STDOUT constant directly for reasons unrelated
to writing to it. When it happens at a point PHP's usual error-display machinery
itself expects a valid STDOUT/STDERR to report through, the failure escalates from a
suppressed warning into something that reports nowhere.

Went with the safer, more surgical fix instead: `ini_set('display_errors', 'stderr')`
(the documented switch for notices/deprecations, PHP docs) plus wrapping boot()'s
config-resolution + container-build step in `ob_start()`/`ob_end_clean()` -- the same
pattern `execute()` already uses around `$application->run()` for Rector's own
raw-echo JSON formatter. Neither touches the STDOUT resource at all. Confirmed with
an E2E scenario (config-boot-output.yaml) whose rector.php echoes during load: clean
JSON-RPC on stdout, exit 0, expected diff produced.

If a future lane wants defense-in-depth against a raw `write(1, ...)` this doesn't
cover (a C-level warning, a segfault dump), reaching for fd surgery is tempting but
should be re-verified against a REAL container boot end-to-end -- not just a
standalone PHP script -- before trusting it. A minimal repro that redirects fds and
prints "it works" is not proof once a real Rector/Symfony DI container is in the
loop.
