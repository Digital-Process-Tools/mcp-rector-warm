#190's fix (`RectorRunner::remapCopyClassesInAutoloader()`) covers two locator
families: a real Composer project (`ClassLoader::addClassMap()`, confirmed
working by a direct unit test, `tests/Unit/RectorRunnerComposerRemapTest.php`)
and a project with no Composer `ClassLoader` registered, via a prepended
`spl_autoload_register(..., prepend: true)` callback that `require`s the
buffer copy when one of its own declared classes is looked up.

Self-review (oss:auditor, #190) raised a mechanism this prepended-autoloader
half cannot be verified against from this repo alone: PHP's autoload chain is
only consulted for a class that is NOT YET DECLARED in the current process
(`class_exists($name)` short-circuits true, with no autoloader call at all,
the instant any earlier code -- PHPStan's generic locator eagerly `require`ing
a file to reflect it, a prior call in a long-lived warm worker, anything else
in the project's own bootstrap -- has already truly loaded a class of that
name). If PHPStan's generic/autoload-based source locator resolves a class by
actually `require`-ing it (rather than merely intercepting the autoloader
callback to read a file path without loading it), a class sharing a name with
something the buffer edits could already be resident by the time
`remapCopyClassesInAutoloader()` registers its prepended callback -- and the
prepend would then never fire for that class, reproducing #190's exact
symptom specifically on the non-Composer path, for specific class names, with
nothing in `execute()` distinguishing "nothing needed remapping" from "could
not remap because the class was already loaded".

Not confirmed: BetterReflection's actual source was not present in this
checkout (`find vendor -iname '*AutoloadSourceLocator*'` returned nothing;
rector/rector ships PHPStan, and BetterReflection inside it, as a phar --
`src/Warm/SessionHooks.php`'s own class docblock already documents this for a
different reason). The Composer-loader half of the same fix was checked
against the real `vendor/composer/ClassLoader.php` source and is clean on
this specific question: `findFile()` checks `$this->classMap` (what
`addClassMap()` overrides) strictly before any APCU-cache lookup, so an
apcu-accelerated project does not defeat that half.

What would settle it: whether `declaredClassLikeNames()`'s target class names
are ever already `class_exists(..., false) === true` at the point
`remapCopyClassesInAutoloader()` runs, for a project using the non-Composer
locator path. The new E2E regression
(`tests/E2E/test_lsp_session.py::test_190_...`) only exercises one diagnostic
call per spawned server process, so it would not surface this even if real.
