A `git worktree add` into `worktree_root` produces a directory with no `.supertool.json` of its
own -- `supertool` refuses every op there ("No .supertool.json was found from <path> or any
parent, so no preset ops and no project ops are loaded"), including `git-status`, `edit:@-` and
`paste:@-`, until the file is copied in from the primary clone (`cp
<clone>/.supertool.json <worktree>/.supertool.json`). `cwd:<worktree-path>` prefixed to the op does
NOT fix this -- the error message explicitly says so ("'cwd:' moves the directory the op ACTS on as
well as the one its config is read from, so it is the fix only when the work is in that project --
never a way to run 'git-status' against THIS directory"), which cost one extra round-trip to
discover by trial. Worth checking whether new worktrees should get `.supertool.json` copied
automatically at creation time (by whatever cuts the worktree -- `lane_setup.py` or the claim step),
since every developer lane's very first supertool call in a fresh worktree hits this.

Separately: this lane's spawn payload named a worktree path
(under the configured `worktree_root`) that already existed on disk (apparently
cut by an earlier step or a recon agent's own exploration) but was checked out `detached` at
`origin/main`'s tip rather than on branch `fix/179` -- `git worktree add -b fix/179 ...` against
that same path failed with "already exists" rather than attaching the branch. `git checkout
fix/179` inside the existing worktree (after confirming the branch existed locally via `git branch
--list`) resolved it. Worth noting for whatever documents the worktree-claim contract: "the
worktree already exists" and "the worktree already exists AND is on the right branch" are two
different states, and only the git-worktrees op's per-tree "occupied"/"idle" + branch name columns
distinguish them -- a lane that only checks "does the directory exist" would silently start working
from the wrong branch.
