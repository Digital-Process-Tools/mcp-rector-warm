Calling ProcessTree::killTree() with the CURRENT process's own pid as $rootPid (e.g. via
getmypid()) SIGSTOPs the calling process as the very first action inside killTree(), before
$excludePids or anything else is consulted. The calling process freezes immediately -- it
never resumes itself, because the code that would resume it never runs once it is stopped.

This was hit while writing a PHPUnit test for killTree() on #245: an early draft called
ProcessTree::killTree(getmypid(), [...]) to exercise the exclusion branch, intending to
target the test's own grandchild process but passing the wrong pid as the root. It froze a
live shared phpunit-mcp validator daemon worker process in state T (SIGSTOP'd), recovered
manually with `kill -CONT <pid>` across several affected pids before the test could be
rewritten correctly.

The fix was procedural, not a code change: always target a disposable child process spawned
via proc_open() for a killTree() test, never getmypid() or any ancestor of the calling
process. The committed test code never calls killTree() on self.

A related, still-open production edge case (not fixed, see PR body / adjacent findings for
#245): killTree() excluding $rootPid from its own $excludePids list hits the same unconditional
SIGSTOP-first ordering and leaves the excluded root frozen in state T forever rather than left
alone, since nothing later in killTree() resumes an excluded pid. No current caller passes
$rootPid as its own exclusion, so this is not fixed in production, only documented.
