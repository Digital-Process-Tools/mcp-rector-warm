Round-2 release audit finding (dispatch token 5f6d34d8b56c), non-blocking, `misreports`.

Two commits combine to change the failure mode of a wedged dryRun:false call, and
the #72 release notes (changelog.d/72.fixed.md, README.md:100,148) describe only
half of it. a8f883b (#32) turned RectorRunner::readExactly()'s socket-read timeout
into an unbounded wait instead of returning null. 7c74e64 (#72) then removed the
only remaining bound -- --call-timeout -- for dryRun:false calls, at all three kill
sites (runForked backstop :474, forkAndExecute's killAndReap call :621, runCold's
proc_terminate :756).

Compared with v0.5.0 (git show v0.5.0:src/RectorRunner.php:551-557,298-308): a
wedged write there timed out the socket read after ~60s (default_socket_timeout)
and the daemon returned "the warm worker closed its connection unexpectedly" and
served the next call. At HEAD a wedged write grandchild blocks the single-threaded
daemon indefinitely -- every later tool call from that client hangs too, not just
the wedged one.

The trade-off itself is sound (the obvious bounded alternative -- stop waiting
without killing -- would let a second worker boot while the old grandchild still
writes the same file, reopening a concurrent-write hazard #72 was fixed to close).
So this is a documentation gap, not a design defect: a v0.5.0 user reading the
0.6.0 notes cannot learn that a wedged write now freezes the whole server where it
used to error after ~60s. Two sentences in the changelog fragment and the README
--call-timeout row would settle it. Also noted by the same audit, reasoned rather
than observed: a dryRun:true kill landing during Rector's own non-atomic cache
copy() (vendor/rector/rector's FileCacheStorage.php:71, loaded by a bare require
at :43) could leave a truncated cache file -- regenerable, so not `destroys`, and
the window is narrow.
