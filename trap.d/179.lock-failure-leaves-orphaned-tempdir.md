Release-auditor round-1 finding on the #179/PR #186 TempCopySweeper redesign (v0.7.2 gate 3,
ranked here as `fails-to-preserve`, non-blocking).

What was observed: a rare interleaving between two LSP servers diagnosing files in the same
directory can leave an orphaned `.rector-warm-<pid>/.lock` behind, empty, with no recorded
basename. Server P `fopen('.lock','c')`s, then before P's own `flock`, server Q's
`sweepDirectory()` sees the lock file exist via `is_file()`, briefly takes `LOCK_EX|LOCK_NB`
and wins it. P's `flock(LOCK_NB)` then fails, P closes its handle and `@rmdir`s -- which fails
because `.lock` is still present -- and P's `finally` block skips its own lock unlink because
`$lockHandle` is no longer a resource by that point, so its own cleanup also fails.

Where: src/Lsp/RectorDiagnosticsSource.php:283-285 (the pre-existing #165 refusal of an
existing temp directory) and :299-307 (the new lock-failure path), together with
TempCopySweeper::removeKnownContents(), which refuses when the recorded basename reads back
as `''` -- exactly what a lock file with no companion entry produces.

What it costs: for the rest of that server's life, every buffer diagnosed in that directory
hits the pre-existing "refusing a pre-existing temp directory" guard, so diagnostics silently
stop working there until the server restarts. No data is lost, nothing is destroyed, and the
directory is hidden project litter rather than a user file.

Likelihood: two LSP servers racing on the same directory within a lock-acquisition window of
a few microseconds. Low, and reasoned rather than observed -- no test exercises "flock fails
after fopen".

The fix, if picked up later: unlink `.lock` in the lock-failure branch before the `rmdir`,
the same as the ordinary success path already does.
