While fixing #90/#91, the first `supertool 'edit:@-'` attempt for a PHP `sprintf(...,
"...%s\\n", ...)` newline escape was refused: I had written `\\n` (a doubled backslash) in the
TOML `new` field, meaning "one literal backslash followed by n", when what the PHP source
actually needs is a single `\n` (the two-character escape sequence PHP itself interprets as a
newline). The guard's refusal message named the exact run and offered both readings
("meant half the run" vs "meant it as written") -- rereading it made the mistake obvious:
a literal block processes no escapes, so what I typed is what lands on disk.

What it cost: one failed edit call and a resend with a single backslash instead of a doubled
one, which then succeeded and produced the correct PHP source.

How it was confirmed: `php -l` on the resulting file passed, and the resulting string in
`RectorDiagnosticsSource.php` reads as a normal PHP double-quoted newline escape, matching
every other newline escape already in that file's neighbouring `sprintf()` calls.

Lesson for the next lane: when writing a PHP (or other language) string literal containing
a newline escape inside a TOML triple-quoted `edit`/`paste` payload, write exactly ONE
backslash -- the TOML literal block does not consume it, so it reaches the PHP source
unchanged. Doubling the backslash "to be safe" puts two on disk and is refused before it
gets that far.
