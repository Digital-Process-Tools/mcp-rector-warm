Round-2 release audit finding (dispatch token 5f6d34d8b56c), non-blocking, `misreports`.

src/Support/ServerVersion.php:49 calls
class_exists(\Composer\InstalledVersions::class, false) with the second argument
false, which disables autoloading. Nothing else in the codebase loads that class
first (vendor/composer/autoload_real.php does not require it; grep for
InstalledVersions under vendor/mcp finds nothing), so this check always returns
false and the Composer-pretty-version branch is dead code.

Observed: `php -r 'require "vendor/autoload.php";
var_dump(class_exists("Composer\\InstalledVersions", false));
echo \App\Support\ServerVersion::resolve();
var_dump(class_exists("Composer\\InstalledVersions", false));'`
printed `bool(false)` / `0.5.0` / `bool(false)`.

Effect: the reported server version always comes from the first `## [x.y.z]`
heading in CHANGELOG.md. The docblock's claim that it is "exact for a tagged
release install" never actually runs (ServerVersionTest:71 already documents
this). In practice the fallback is usually right, since CHANGELOG.md ships in
the dist -- it goes wrong only if a tag is ever cut without folding the
changelog first, or if CHANGELOG.md is later export-ignored from the package.

What would settle it: drop the `false` argument (allow autoloading) and confirm
resolve() then returns Composer's own installed pretty version instead of
falling back to the changelog heading.
