Self-review flagged (Explore reviewer, spawned against commit cafc09d) that the #14
fix is narrower than its own comments/README first claimed: `RectorRunner::boot()`
only refuses when `RectorConfigsResolver`/`BootstrapConfigs::getMainConfigFile()` is
`null` -- i.e. no `--config` and no `rector.php`/`rector.dist.php` in the working
directory at all. Prose was narrowed to say exactly this (src/RectorRunner.php's
comment, README.md's "How it works" bullet 4); this fragment is about what is left
unfixed, not about the prose.

The mechanism #14 targets -- `SymfonyStyle`'s `ConsoleOutput` writing a warning
straight to the real stdout (bypassing `ob_start()`), plus `Command::SUCCESS` for a
call that did nothing -- is still fully reachable through a DIFFERENT, broader
condition: `ProcessCommand::execute()`'s own `!$this->configInitializer
->areSomeRectorsLoaded()` check (vendor/rector/rector/src/Console/Command/
ProcessCommand.php:131), which fires whenever the active (non-post) rector list is
empty. A `rector.php` that exists, loads without error, but never calls
`->withRules()`/`->withSets()` (or has all its rules filtered out) hits this exact
path: `getMainConfigFile()` is non-null so `boot()`'s new guard never fires, the
container builds normally, and later, mid-`process`-command, `ConfigInitializer::
createConfig()` calls `$symfonyStyle->warning(...)` on a `ConsoleOutput` that opens
`php://stdout` directly -- independent of the `BufferedOutput` `RectorRunner::
execute()` passes into `$application->run()` -- and `ProcessCommand` returns
`Command::SUCCESS` regardless.

Not fixed here: closing this needs either (a) inspecting the resolved rule set for
emptiness before/without building the full DI container (unclear whether Rector
exposes that cheaply), or (b) building the container and checking the equivalent of
`areSomeRectorsLoaded()` post-boot, inside the ob_start() wrap that already guards
boot() -- both are design decisions past what #14 (titled "no rector.php and no
--config") asked for, and reaching into ProcessCommand's own execute()-time check
from a wrapper this far outside Rector's own console layer is not a one-line change.

Reachable, real, same subsystem, not the same issue: whoever picks this up next
should treat it as its own filed issue rather than folding it into #14/#15.
