What was observed: `rmdir($tmp)` in
tests/Unit/RectorRunnerTest.php::testColdCallIsKilledAtItsDeadlineWithoutPcntl's
`finally` block failed with a PHPUnit warning on windows-latest only:
`rmdir(...Temp/rector-runner-cold-timeout-test-<hex>): Resource temporarily
unavailable`. `failOnWarning="true"` in phpunit.xml turned that one warning
into a red CI leg (exit 1) even though all 105 tests passed. Only the outer
`rmdir($tmp)` warned; the sibling `rmdir($tmp . '/src')` two lines above never
did.

Where: PR #104, `tests (windows-latest, 8.3)` leg, job #109005659983 (run
#36445222576, commit 26973bb -- the commit that added `--display-warnings`
to `.github/workflows/tests.yml` and is what made the previously-invisible
warning detail block visible in the log; see trap.d/97 for that half of the
story).

What it cost: two lanes across the #97/#96 arc -- one to get the warning's
text visible at all (trap.d/97), a second to diagnose and fix it once
visible. Neither could reproduce locally: this repo has no Windows CI runner
available to a lane, and the race does not occur on POSIX (confirmed: 18
consecutive local runs of the same test on macOS/Darwin, zero rmdir
failures) -- POSIX kills release the child's file handles synchronously with
the kill signal, Windows's TerminateProcess() does not.

Mechanism: the test's cold subprocess (spawned via
RectorRunner::runCold()) has `chdir($tmp)`'d as its cwd before being
spawned; the test forces the no-pcntl deadline-kill path, which
`proc_terminate()`s + `proc_close()`s the child at its 5s deadline but does
not itself wait for the OS to confirm the child's file handles (including
its handle on its own cwd) have been released before returning control to
the caller. On Windows this leaves a short window where $tmp is still
locked when the test's own `finally` cleanup tries to `rmdir()` it. This is
narrower than a logic bug in the no-pcntl kill path itself (#8, unrelated
and already correct) -- it is a cleanup-ordering assumption that only
Windows violates.

How it was confirmed: fixed by adding a `rmdirWithRetry()` helper to
RectorRunnerTest (originally 10 attempts, 100ms usleep backoff between each,
matching runCold()'s own poll interval; lets the final attempt's real error
surface rather than swallowing it forever) and wrapping both `rmdir()` calls
in testColdCallIsKilledAtItsDeadlineWithoutPcntl's `finally` block with it.
Verified locally on macOS/Darwin only: the fixed test and its sibling
(testColdCallReportsRealExitCodeWithoutPcntl) both pass, and the retry loop
takes its fast path (first rmdir() attempt succeeds, no backoff) every time
there -- this is REASONED, not OBSERVED, for the actual Windows race the fix
targets, since the race is Windows-only by construction and no Windows
machine was available to this lane either. The real signal is the next
windows-latest CI run on this branch.

Widened mitigation (issue #96, second pass): the original ~900ms budget was
exceeded again on PR #104's `tests (windows-latest, 8.3)` leg. Root cause is
issue #114 -- a leaked grandchild php process on Windows that can hold the
directory handle open for a few seconds while the OS reaps it, well past the
900ms the original retry budgeted for a single short-lived handle. #114 is
the real fix (terminating the whole process tree, not just the immediate
child) and is deliberately NOT fixed here -- it is a production
process-tree-termination change that needs its own review, not something to
fold into a test-side retry tweak. Instead `rmdirWithRetry()`'s budget was
widened to give real headroom against a leaked process that takes a few
seconds to exit or get reaped: 12 attempts, starting at 150ms and
multiplying by 1.5 up to a 1s cap, ~8s of total backoff (up from ~900ms) --
short exponential backoff rather than 12+ fixed-100ms attempts, so it does
not hammer the filesystem. `retryUntilTrue()` gained an optional
`$backoffMultiplier`/`$maxDelayMicroseconds`/`$sleep` (test-injectable
in place of a real `usleep()`) to support this; a multiplier of 1.0 (the
prior implicit behaviour) keeps the delay fixed, so no existing caller's
semantics changed. Two new unit tests pin the widened mechanics directly via
the injected `$sleep` spy (`testRetryUntilTrueBackoffGrowsThenCaps`,
`testRmdirWithRetryDefaultBudgetTotalsAroundEightSeconds`), running
instantly despite covering an ~8s real-world budget; the two original
pinning tests (call-count/final-flag shape, delay=0) needed no changes since
they exercise `retryUntilTrue()`'s generic mechanics independently of
`rmdirWithRetry()`'s concrete constants. This second pass is REASONED, not
OBSERVED, same as the first -- verified locally on macOS/Darwin only (fast
path, first attempt succeeds), and the real signal is again the next
windows-latest CI run.

Left un-touched, on purpose: the identically-shaped
`rmdir($tmp . '/src'); rmdir($tmp);` cleanup in the neighboring
testColdCallReportsRealExitCodeWithoutPcntl (#73) test was NOT given the
same retry -- that test's rule calls exit(7) itself (a clean self-exit
inside the deadline, never hits the TerminateProcess()/kill path), so it is
not exposed to this same race and has never shown the warning in a captured
log. Worth revisiting if it ever does.

Self-review addendum: the first version of this fix had an off-by-one --
the loop's final iteration called the suppressed `@rmdir()` once more
(attempt "10") and then, since that also failed, immediately called the
unsuppressed `rmdir()` a second time with no backoff in between -- 11
physical calls against a docblock and commit message both saying "10
attempts", and zero backoff before the one call whose error is allowed to
surface. Caught by a reviewer (Explore, self-review round) before push,
because no test in this repo exercised the retry loop's own mechanics --
only the fast (first-attempt-succeeds) path, which is all POSIX ever hits.
Fixed by extracting the loop into a small generic `retryUntilTrue()`
helper and adding two unit tests that pin its call count and backoff
shape directly (`testRetryUntilTrueStopsAsSoonAsAttemptSucceeds`,
`testRetryUntilTrueMakesExactlyAttemptsCallsAndMarksOnlyTheLastFinal`) --
confirmed red against the reintroduced old behaviour, green against the
fix, both by hand in this lane. Lesson for whoever promotes this: a retry
helper's own mechanics (attempt count, which attempt is "final", backoff
timing) need a test independent of whatever external race it exists to
paper over, because the race itself may never reproduce in this suite at
all (this one is Windows-only) -- and a bug in the retry logic then ships
invisibly behind a docblock that describes the intended behaviour, not the
actual one.
